# Lyapunov 0.2.0 Alpha 1 (candidate)

The first 0.2.0 alpha adds the **agent graph**: a verified skill-refinement campaign layer on top of the existing agent loop, adapted from NVIDIA ASPIRE's coordinator/worker/verifier protocol onto Lyapunov's typed scene, generation and receipt contracts. No agent-loop internals changed — everything mounts on documented extension points. The version is `0.2.0-alpha.1`, a candidate prerelease built on top of `0.1.0-rc`.

## Changes in this release

- **Deterministic task checks (`sim_task_check`).** A new tool evaluates task predicates against the live world without stepping physics: `entity-in-box`, `distance-below`/`above`, `contact-exists`, `joint-in-range`, `settled`, `reachable`, `no-penetration`, composed with `and`/`or`/`not`. Every failure returns a named `reasonCode` with expected vs measured readings, so a worker repairs against facts instead of retrying blind. Spec-level gates (`SPEC_ENTITY_MISSING`, `SPEC_UNREACHABLE`, `SPEC_ALREADY_SATISFIED`) reject before evaluation, and missing data reports `OBSERVATION_UNAVAILABLE` rather than guessing.
- **Inline predicate evaluation on action tools.** `robot_move`, `joint_move`, `vehicle_drive`, `robot_gripper`, `robot_walk` and `sim_execute_batch` accept an optional `predicates` field (same contract as `sim_task_check`). When supplied, the post-action frame is evaluated and the receipt carries the real `taskAchieved`, a `reason` joined from the failed `reasonCode`s, and the full `taskCheck` detail — upgrading the placeholder `taskAchieved:false` into measured truth without opening a campaign. Calls without `predicates` keep the existing action path.
- **Campaign orchestration (`campaign_*`).** `campaign_init` registers a task set partitioned into `dev` and `heldout`, `campaign_transition` drives a state machine (`pending → exploring → debugging → verifying → heldout-eval → done|blocked|rejected`), `campaign_status` reads the whole board, and `campaign_record_run` closes each run with a self-contained summary. Worker runs may never touch heldout tasks (`CAMPAIGN_PARTITION_VIOLATION`); heldout evaluation is a coordinator-only edge.
- **Deterministic curriculum pointer.** `campaign_init` and `campaign_status` return `recommendedNextTaskId`: the pending `dev` task with the lowest predicate-atom count (simpler goals first), falling back to the first pending `heldout` task once dev work settles — so the coordinator's next move is computed, not guessed.
- **Run artifacts and budget guardrails.** A `tools/execute` waterfall collector writes `calls.jsonl` per run — every tool call with a SHA-256 argument digest and the receipt fields (generation, revisions, steps, status, `taskAchieved`) — plus `run.json` on close, under `.lyapunov/campaigns/<id>/`. Three budget axes (`maxToolCalls`, `maxSimSteps`, `maxWallSeconds`) let the breaching call finish and then refuse further dispatches with `CAMPAIGN_BUDGET_EXCEEDED`; `campaign_*` tools stay exempt so a coordinator can always record and wind down.
- **Hard partition and blind-review isolation.** Inside the same waterfall, a worker run whose call arguments reference a `sceneId` bound to a heldout task is rejected with `CAMPAIGN_PARTITION_VIOLATION` — including mutation tools (`scene_edit`, `scene_mount`, `robot_set_*`, assembly ops) even on its own scene when that scene is heldout-associated. A verifier run whose arguments touch `.lyapunov/campaigns` proposer artifacts is rejected with `CAMPAIGN_VERIFIER_ISOLATION`. Every rejected dispatch is still recorded as an error row in `calls.jsonl`, so the refusal itself is evidence.
- **Verifier-admitted skill library.** `packs/<id>/skills/` now holds promoted skills; proposals live under `packs/<id>/proposals/` until a verifier independently reproduces the fix on held-out-free dev instances. `skill_propose`, `skill_verify_record`, `skill_promote` and `pack_skill_list`/`pack_skill_get` implement the admission pipeline; promotion requires a `passed:true` verify record and lands in `promotions.jsonl` (`SKILL_NOT_VERIFIED` otherwise). A verifier run id that collides with the proposal's own `devEvidence.runIds` is rejected as self-review. An admitted skill carries its failure signature, applicability, fix strategy, program sketch and evidence run ids.
- **Automatic skill recall on failure (`matchedSkills`).** When `sim_task_check` — standalone or inline on an action tool — reports failed predicates, the admitted skill library is scanned for `failureSignature.reasonCodes` intersecting the failure set, and the result carries `matchedSkills:[{packId, skillId, fixStrategy, reasonCodes}]`. A worker sees the proven fix beside the error instead of having to remember to query the library.
- **Command-path parity.** `/sim_task_check`, `/campaign_*`, `/skill_*` and `/pack_skill_*` slash commands dispatch through `ctx.tools.execute`, so waterfall observers, artifact collection, privacy projection and campaign state projection see exactly the same results as model tool calls; the command domain whitelist admits the new names for non-composer callers.
- **Agent skills for the three roles.** `.agents/skills/skill-debug` (worker fix-loop), `skill-campaign` (coordinator: curriculum ordering, heldout sweep, rerun on library change) and `skill-verify` (verifier: library-and-proposal only, no proposer artifacts, ≤2 attempts) describe the protocols in terms of the frozen tool names.
- **Workbench campaign view.** A `campaigns` session projection folds `campaign_*` receipts into a task-status matrix with per-task partition badges and a used/max budget meter, logged as the ignorable `lyapunov/campaign-state` session event so panels replay from the session log. A dedicated **Campaigns** tool-rail entry opens the panel inside the workbench, and command cards render localized titles and failed-predicate summaries for `sim_task_check` and the campaign/skill commands.

## Verified scope and boundaries

- Unit and integration coverage: predicate evaluation per kind plus combinators and spec gates, campaign state machine transitions and partition rules, artifact collection and all three budget axes, the cross-package end-to-end chain `init → transition → artifacts → record_run → propose → verify → promote`, and the closed-loop additions (inline `predicates` enrichment, `matchedSkills` recall, heldout-scene and verifier isolation, `recommendedNextTaskId`) — 182 tests pass across the touched packages.
- Release gates on the packaged candidate: GitHub Actions green on the packaged source commit (`6d07f53`), root release gate 19/19 with 408/408 offline tests, `verify-package` all-passed with `sourceCommitMatchesPayload`, and a real packaged-desktop acceptance run (20/20 checks through the live `/api/lyapunov/command` route, including both isolation refusals landing named codes in `calls.jsonl`, a real MuJoCo world evaluation producing `matchedSkills`, and the Campaigns panel reading live state).
- Heldout tasks are deliberately inert for workers: only the coordinator may evaluate them, and results are recorded, never re-opened for debugging — this is what keeps heldout honest.
- Run ownership is per session: a worker run belongs to the session that opened it; cross-session worker assignment is a known boundary for this alpha.
- Budgets are a watchdog, not a sandbox: they bound a campaign's tool use but are not a security boundary.
- ASPIRE is a protocol reference, not a runtime dependency: no ASPIRE code ships; the campaign shape was re-implemented on Lyapunov's receipts and contracts.
- Public-facing command errors keep the established privacy contract: internal refusal codes surface on the human face as `P422`/`P500` plus a redacted message, while the named code (`CAMPAIGN_PARTITION_VIOLATION`, `CAMPAIGN_VERIFIER_ISOLATION`, `CAMPAIGN_BUDGET_EXCEEDED`) is recorded verbatim in `calls.jsonl` and host logs.
